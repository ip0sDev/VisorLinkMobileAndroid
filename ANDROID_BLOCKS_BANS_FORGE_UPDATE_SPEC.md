## 0. Порядок выкатки и что ломает старый Android

Эти изменения **ломают сборки Android, выпущенные раньше**. Релиз Android должен выйти **до** шагов 3–4.

| Шаг | Что деплоится | Что без обновления Android сломается |
|---|---|---|
| 1 | **Android-релиз** (этот документ) | — |
| 2 | Функции (`Guards.js` изменён — деплоится практически весь `functions`) | Заблокированный сервисом аккаунт получает `permission-denied` / `reason: 'banned'` на любые вызовы; старый клиент покажет общую ошибку |
| 3 | `firestore.rules`, `storage.rules` | **Запись `users.blockedUsers` запрещена** (старая блокировка пользователя перестаёт работать — нужен `setUserBlock`); `users/{uid}` и `idCards/{uid}` могут отвечать `permission-denied` (пользователь заблокировал вас); заблокированный сервисом аккаунт теряет доступ к Firestore |
| 4 | `database.rules.json` | **Узел `presence` целиком больше не читается.** Клиент, который слушает `presence` одним `addValueEventListener`, получит `PERMISSION_DENIED` — пропадут все индикаторы «в сети». Нужно слушать `presence/{uid}` по одному (как делает веб) |

Что обязательно сделать в Android **до** шага 4:
1. Заменить слушатель всего узла `presence` на слушатели `presence/{uid}` для нужных пользователей (собеседники в списке чатов, шапка, профиль; для групп — только участники, лимит как в вебе: **не больше 100** участников, иначе счётчик «в сети» не считается).
2. Обрабатывать `onCancelled` / `PERMISSION_DENIED` слушателя `presence/{uid}` как «офлайн» (так отвечает база, если пользователь вас заблокировал).
3. Обрабатывать `permission-denied` при чтении `users/{uid}` и `idCards/{uid}` (см. §2.5).

## 1. Блокировка аккаунта сервисом (баны) и апелляции

Администратор сервиса блокирует аккаунт. Доступ закрывается **сразу и жёстко**, все сессии завершаются, но заблокированный
**может войти**, чтобы увидеть причину и **один раз** отправить апелляцию до **300 символов**.

### 1.1. Модель данных

| Где | Поле | Кто пишет | Смысл |
|---|---|---|---|
| `users/{uid}` | `banned: true` | только сервер | Флаг блокировки. Клиентам запрещено писать `banned`, `banReason`, `bannedAt`, `bannedBy` |
| `users/{uid}` | `banReason: string` | сервер | Причина (≤ 200 символов, «Нарушение правил сервиса» по умолчанию) |
| `users/{uid}` | `bannedAt` | сервер | Время блокировки |
| `bans/{uid}` | `reason`, `bannedAt`, `bannedBy`, `appeal`, `appealStatus`, `resolutionNote?` | только сервер | Запись о блокировке. **Читает только сам заблокированный** (`get`), `list` и запись запрещены |
| RTDB `bans/{uid}` | `true` | сервер | Зеркало для правил RTDB; клиентам недоступно |

`bans/{uid}`:

```
reason:         string
bannedAt:       Timestamp
bannedBy:       string                       // uid админа
appeal:         null | { text: string, createdAt: Timestamp }
appealStatus:   "none" | "pending" | "rejected"
resolutionNote: string?                      // заметка админа при отклонении, ≤ 200 символов
```

Когда блокировку снимают, `users.banned/banReason/bannedAt` **удаляются**, документ `bans/{uid}` **удаляется**. Повторная
блокировка создаёт новый `bans/{uid}` — и **новую единственную апелляцию**.

### 1.2. Что происходит при блокировке (сервер, `adminSetBan`)

1. `users/{uid}.banned = true` — **с этого момента** правила Firestore и все серверные функции отказывают.
2. `bans/{uid}`, RTDB `bans/{uid}`, присутствие → офлайн.
3. `revokeRefreshTokens(uid)` — **все refresh-токены отозваны**: ни одна сессия не продлится.
4. Запись в `audit_logs`.

Аккаунт Firebase Auth **не отключается** (`disabled` не ставится): иначе заблокированный не смог бы войти и подать апелляцию.
Администратора заблокировать нельзя.

### 1.3. Что закрыто для заблокированного

- **Firestore:** `isFullyVerified()` для него ложно → все чтения и записи, кроме: чтения **собственного** `users/{uid}`
  (нужно, чтобы увидеть `banned`) и собственного `bans/{uid}`.
- **Cloud Functions:** все, кто проходит `requireVerified`, отвечают `permission-denied` с `details.reason == "banned"`.
  Исключения (доступны заблокированному): `submitBanAppeal`, `requestMyDataArchive` (выгрузка своих данных),
  функции удаления аккаунта (`requestAccountDeletion`, `cancelAccountDeletion`).
- **RTDB:** запрещены чтение и запись `presence`, `typing`, `users/{uid}`.
- **Storage:** запрещена загрузка файлов (чтение не проверяется).

### 1.4. Что делает Android

**Обнаружение.** Профиль `users/{uid}` читается и так (подписка на собственный документ). Если `banned == true` — вместо
всего приложения показать **экран блокировки**. Подписка на профиль работает и у заблокированного (правило разрешает
читать свой документ), поэтому при снятии блокировки приложение вернётся само.

**Токены.** После блокировки refresh-токен отозван: при ближайшем обновлении ID-токена SDK вернёт ошибку
(`FirebaseAuthInvalidUserException` с кодом `ERROR_USER_TOKEN_EXPIRED`), а `FirebaseAuth` может разлогинить пользователя.
Это ожидаемо — человек входит заново и попадает на тот же экран блокировки. **Не** зацикливайте автовход и **не**
считайте это ошибкой сессии (`session-revoked`) — это другая ситуация.

**Экран блокировки** (повторяет `BannedScreen.jsx`):

- Иконка/заголовок «Аккаунт заблокирован», пояснение, блок «Причина» (из `bans/{uid}.reason`, запасной вариант —
  `users/{uid}.banReason`).
- Подписка на `bans/{uid}` (допускается `PERMISSION_DENIED` — тогда считать, что записи нет, и показать форму: сервер всё
  равно проверит).
- По `appealStatus`:
  - `none` — форма апелляции: текстовое поле, счётчик `N / 300`, подсказка «Апелляцию можно отправить только один раз, до 300 символов»,
    кнопка «Отправить апелляцию» (отключена при пустом тексте и при > 300);
  - `pending` — «Апелляция отправлена. Мы рассмотрим её…», показать свой текст (`appeal.text`);
  - `rejected` — «Апелляция отклонена», `resolutionNote` (если есть), свой текст.
- Внизу: «Выйти», «Условия использования», «Удалить аккаунт» (оба последних — внешние страницы
  `/terms-of-service` и `/delete-account` в браузере/Custom Tab). Всё остальное приложение не рендерится.

**Длина.** Сервер считает **символы (code points)**, а не UTF-16: эмодзи — один символ. В Kotlin использовать
`text.codePointCount(0, text.length)` (не `length`). Ограничение поля ввода по `length` оставлять **нельзя** — оно
отрежет эмодзи. Пробелы по краям и управляющие символы сервер убирает; пустое после очистки отклоняется.

**Отправка:** callable `submitBanAppeal`, регион `europe-west1`:

```json
{ "text": "…" }
```

Ответ `{ "success": true }`. После этого подписка на `bans/{uid}` сама пришлёт `appealStatus: "pending"`.
Ошибки (`FirebaseFunctionsException`, смотреть `details["reason"]`):

| Код | `reason` | Что показать |
|---|---|---|
| `invalid-argument` | `empty` | «Напишите текст апелляции» |
| `invalid-argument` | `too-long` | «Не больше 300 символов» |
| `already-exists` | `already-sent` | «Апелляция уже была отправлена — повторно её подать нельзя» |
| `failed-precondition` | `not-banned` | «Аккаунт уже не заблокирован — обновите» |
| любая другая | — | «Не удалось отправить. Попробуйте позже» |

Кнопку после успешной отправки нужно сразу скрыть: повторная отправка вернёт `already-sent`. Апелляция **ровно одна** на
блокировку — и после отклонения подать новую нельзя.

**Остальные вызовы.** Любой вызов функции, вернувший `permission-denied` с `reason == "banned"`, означает блокировку:
не показывать «ошибку сети», а перейти на экран блокировки (профиль, скорее всего, уже подтянется).

### 1.5. Что НЕ нужно в Android

Админка блокировок (`adminSetBan`, `adminListBans`, `adminResolveAppeal`) — только веб. Android-клиент ими не пользуется.

## 2. Блокировка пользователя пользователем

Раньше «Заблокировать» только писало uid в **открытое** поле `users/{я}.blockedUsers`: его читали все, и ничего не
проверялось. Теперь это настоящая блокировка с приватными списками. Модель — как у Instagram: заблокированный **не видит
профиль и «в сети» блокирующего и не может ему писать**.

### 2.1. Модель данных (всё пишет только сервер, функция `setUserBlock`)

| Где | Читает | Содержимое |
|---|---|---|
| Firestore `blocks/{я}/users/{они}` | только `{я}` | «кого заблокировал я»; поле `createdAt` |
| Firestore `blockedBy/{я}/users/{они}` | только `{я}` | «кто заблокировал меня» (зеркало); поле `createdAt` |
| RTDB `blocks/{я}/{они}` | только `{я}` | зеркало для правил `presence` |
| `users/{я}.blockedUsers` | — | **устарело, клиентам запрещено писать** |

Подписка на `blockedBy/{мой uid}/users` (коллекция) — **одна на весь список** тех, кто вас заблокировал; не нужно слушать
документ на каждого собеседника. Аналогично `blocks/{мой uid}/users` — ваш список блокировок.

### 2.2. Вызов

Callable `setUserBlock`, регион `europe-west1`:

```json
{ "targetUid": "<uid>", "blocked": true }
```

`blocked: false` — разблокировать. Ответ `{ "success": true, "blocked": <bool> }`. Ошибки: `invalid-argument` (плохой uid,
нельзя заблокировать себя), `not-found` (нет такого пользователя), `resource-exhausted` (лимит — **1000** блокировок).
**Никогда не писать `users/{я}.blockedUsers` напрямую** — правила запрещают.

### 2.3. Что делает блокировка (серверно, правилами и функциями)

В личном чате действует **в обе стороны**: пока блокировка есть, не может писать ни заблокированный, ни блокирующий
(блокирующему нужно сначала разблокировать — как в Telegram).

| Действие | Результат |
|---|---|
| Создать сообщение в личном чате | отказ правил (`PERMISSION_DENIED`) |
| Реакции (`reactions`, `reactions + readBy`) на сообщения личного чата | отказ правил |
| Фото-альбом `sendAlbum`, публикация ID-карты в чат | `permission-denied`, `details.reason`: `blocked-by-peer` / `blocked-by-me` |
| `createDirectChat` с тем, кто заблокировал вас | `permission-denied`, `reason: "blocked-by-peer"` (чат не создаётся) |
| Приглашение в группу `inviteUser` от заблокированного | `failed-precondition` «Пользователь не принимает приглашения» (причина не раскрывается) |
| Чтение `users/{блокирующий}` | отказ правил (`PERMISSION_DENIED`) — аватарка, `lastMessageAt` и остальное закрыты |
| Чтение `idCards/{блокирующий}` | отказ правил |
| Чтение RTDB `presence/{блокирующий}` | отказ правил → считать «офлайн» |

Создание личного чата **клиентом напрямую** (правило `isValidDirectChatCreate`) тоже запрещено, если собеседник вас заблокировал.

### 2.4. Что делает Android

- Подписаться на `blockedBy/{uid}/users` и `blocks/{uid}/users` (два `SnapshotListener` на всё приложение; кэш `Set<String>`).
- **Блокировка меня** (`peer ∈ blockedBy`): в списке чатов и шапке — **инициал вместо аватарки**, «в сети» не показывать,
  вместо «был(а) …» писать «был(а) давно» (`chat.lastSeenLongAgo` — «был(а) давно» / «last seen a long time ago»);
  индикатор «печатает» — не показывать; поле ввода **отключено** с подписью «Вы не можете писать этому пользователю»;
  вложения и отправка недоступны. Профиль — «Профиль недоступен» (`profile.unavailable`).
- **Я заблокировал** (`peer ∈ blocks`): поле ввода отключено с подписью «Вы заблокировали этого пользователя»;
  «печатает» от этого пользователя в чате **и в списке чатов** не показывать (в списке чатов узел `typing` слушается целиком —
  отфильтровать по `blocks`). В профиле — кнопка «Разблокировать».
- Строки (взять из `src/locales/{ru,en}.json`): `chat.blockedByPeer`, `chat.blockedByMe`, `chat.lastSeenLongAgo`,
  `profile.unavailable`, `profile.block`, `profile.unblock`.
- **Тест на надёжность:** отправка сообщения заблокированному вернёт `PERMISSION_DENIED` — это не должно ломать очередь
  отправки (не повторять бесконечно, пометить сообщение ошибкой).

### 2.5. Закрытые профили: `permission-denied` — нормальный ответ

`users/{uid}` и `idCards/{uid}` теперь могут отвечать `permission-denied` на `get`/слушатель, если этот пользователь вас
заблокировал. Это **не сбой**: слушатель завершается, данные остаются пустыми. Нужно:

- в каждом слушателе профиля другого пользователя добавить обработчик ошибки (иначе необработанное исключение / ANR-лог);
- имя и `@username` в списке чатов брать из `chats/{id}.participantData` (там они остаются), **аватарку из `participantData`
  не показывать, если вас заблокировали** — сервер при блокировке пишет `participantData.{блокирующий}.avatarUrl = null`
  в существующем личном чате и возвращает при разблокировке;
- не пытаться повторять запрос в цикле.

### 2.6. Создание личного чата (Android создаёт его напрямую)

Правила разрешают клиенту создать личный чат строгой формы. Добавлено условие: **нельзя создать чат, если собеседник вас
заблокировал**. Дополнительно: если **вы** заблокировали собеседника, при создании чата пишите
`participantData[вашUid].avatarUrl = null` (иначе собеседник увидит вашу аватарку в данных чата). Надёжнее — вызывать
`createDirectChat` (веб так и делает): функция делает это сама и возвращает существующий чат, если он уже есть.

### 2.7. Известные ограничения (так задумано)

- В **группах** блокирующий остаётся виден: профиль участников и `senderAvatarUrl` в сообщениях общие.
- Уже выданные прямые ссылки на файлы аватарок остаются рабочими (их нельзя отозвать); скрыто получение через сервис.
- Узел `typing` читают все вошедшие; в личном чате блокирующий не печатает (поле ввода отключено), а чужое «печатает» он
  не показывает на своей стороне.

## 3. Возраст 16+ в соглашениях

**Требования Android уже описаны** в `docs/ANDROID_COMPLIANCE.md` §8 (документы v1.4.0) и `docs/MOBILE_LEGAL_CONSENT_SPEC.md`;
здесь — краткое напоминание и результат сверки по репозиторию.

### 3.1. Что должно быть в Android

- Чекбокс **«Мне исполнилось 16 лет.»** (en: «I am 16 or older.»), без варианта «с согласия родителей».
- `recordUserLegalConsent` отправляет `agreeAge16: true` (поле `agreeAge14` больше не существует); сервер пишет
  `users/{uid}.age16Confirmed`.
- Версия документов — **1.4.0**; повторное согласие у всех, кто принял 1.3.0 и ниже; версию брать из загруженного документа,
  не из константы.
- Возрастной рейтинг / Data Safety / целевая аудитория в Play Console — **16+** (не «Дети/Семьи»).
- Подстановка `{{OPERATOR}}` в юридических текстах (см. `ANDROID_COMPLIANCE.md` §8.3).
- Старые сборки без `agreeAge16` **не пройдут** экран согласия (сервер отвечает `invalid-argument` «…обновите приложение»).
- Дополнительно: на экране входа/лендинга и в карточке Google Play указывать «16+»; на вебе добавлена пометка «16+» в футер
  главной страницы.

| Политика обработки ПД (`legal_personal_data_policy.json`, `_en`) — бейдж «Возраст 16+», п. 2.1–2.3, волеизъявления «подтверждение возраста 16+» | 16+ ✔ |

## 4. Forge: что изменилось и как это переносить

Forge — единая тема для нестандартных режимов ID-карты, два оттенка: **Protogen** (циан/маджента) и **Beast** (янтарь).
Только тёмная. Режим и контекст определяют тему (`idcard/ModeThemeSync.jsx`, `utils/modeTheme.js`; логика — в
`docs/ANDROID_ID_CARDS_SPEC.md`). Здесь — визуальные правила, чтобы Android совпадал с вебом.

### 4.1. Изменения последних правок

- **Сканлайнов нет.** Полосы поверх интерфейса убраны полностью: мешали читать текст и картинки. Не добавлять
  оверлеи поверх контента (ни линий, ни «шума»).
- **Рамки по краям окна (HUD-уголки) убраны** — налезали на интерфейс. Никаких декоративных рамок поверх UI.
- **Пустой экран чата — радар вокруг логотипа:** центр колец = центр логотипа (150 dp). Тонкие кольца каждые **54 dp**,
  перекрестие, луч с шлейфом внутри круга радиусом **160 dp**, оборот **8 с**, края плавно гаснут (`primary` с прозрачностью
  14–16 %); при «уменьшить анимацию» луч не вращается. Только на пустом экране чата.
- **Хроматическая аберрация при наведении** (веб; на Android — при нажатии/фокусе по желанию): название чата в списке и
  основная кнопка получают тени `secondary` (слева) и `primary` (справа) по 1 dp. Не обязательно для Android.
- **Меню действий над сообщением** — см. §5.
- **Цвет профиля в Forge** — не заменяет неон режима, а становится вторым цветом `--secondary`: кромка своих пузырей,
  непрочитанное, акценты рамок (`utils/profileAccent.js`).
- Логотип и **круглые аватарки не трогаем** (остаются круглыми).

### 4.3. Правила форм и компонентов (Protogen; Beast — то же без глитча и мадженты)

- **Срезанные углы** (в Compose — `CutCornerShape`): элементы списка чатов — **8 dp**; модальные окна — **14 dp**;
  основные кнопки — **8 dp**, кнопка отправки и «Новый» — **6 dp**; поле ввода — **8 dp**. Иконочные кнопки — квадрат с
  радиусом 2 dp и контуром `forgeLine`.
- **Пузыри:** свой — срез **справа сверху и слева снизу** (12 dp), чужой — **зеркально** (слева сверху и справа снизу).
  Рамка: свой — градиент `primary → secondary` 1 dp, чужой — `forgeLineStrong` 1 dp; диагональ среза дорисована той же
  линией (clip обрезает бордюр, поэтому линию среза рисуют отдельно).
- **Фон:** сетка `primary` 5 % с шагом **44 dp** под интерфейсом + виньетка (радиальный градиент до `#000` 55 % по краям).
  Beast — без сетки, только тёплое пятно (`tertiary` 6 %) в левом нижнем углу.
- **Типографика:** заголовок раздела — моно, капитель, `letterSpacing` 0,08 em; метки разделов — 11 sp, `primary` 85 %,
  у Protogen с префиксом «> »; заголовки модалок — Chakra Petch, капитель, 0,14 em; подпись шапки чата — моно 11 sp, капитель.
- **Кнопки:** основная — контур `primary`, заливка `primary` 14 % поверх `surfaceContainer`, текст `primary`, моно 13 sp
  жирный, капитель, 0,16 em, внутреннее свечение 16 % (при нажатии 22–30 %). Без внешнего свечения (его срезает clip).
- **Сайдбар:** вкладки — прозрачные, моно 12 sp капитель, активная — линия 2 dp `primary` снизу и градиент 10 % вверх;
  выбранный чат — градиент `primary` 16 % → 3 % слева направо, имя `primary`.
- **Непрочитанное** — цвет `secondary` (маджента или цвет профиля), срез 4 dp — чтобы не сливалось с выбранным чатом.
- **Индикатор «печатает»** — квадратные точки 5 dp `primary`.
- **Медиа не загрузилось** — «потеря сигнала»: рамка `warning` 35 %, фон с редкими линиями `primary` 7 % / `secondary` 5 %,
  по центру надпись **SIGNAL LOST**, моно 11 sp жирный, `warning`, 0,16 em.
- **Разделы настроек:** нумерация `01`, `02`… моно 10 sp `text3`; выбранный — срез 8 dp, градиент `primary` 16 %, номер `primary`, справа «▸».
- **Пустой экран чата:** радар (см. §4.1).
- **Сигнал / структура.** Глубина — нейтральные контуры; цветное свечение — только фокус, выбранное, непрочитанное, и **не больше
  одного светящегося элемента на экран**.
- **Светлой версии нет:** в нестандартном режиме переключатель светлой темы недоступен.

### 4.4. Что в Forge **не** переносить

Эффекты, заметные только курсором (hover-аберрация, блочный курсор ввода `caret-shape`), и всё, что зависит от
`clip-path` для свечения: на Android эквиваленты не нужны.

## 5. Меню действий над сообщением

На вебе четыре круглые кнопки рядом с пузырём (реакция / ответить / переслать / удалить) заменены меню как в Telegram.
На Android долгое нажатие на сообщение, скорее всего, уже открывает меню — приведите состав и порядок к вебу.

**Меню** (по правой кнопке мыши / долгому нажатию 500 мс):

1. **Строка реакций:** первые **6** самых используемых реакций + стрелка «больше реакций» (раскрывает полный список с переносом).
2. Пункты в порядке: **Ответить** → **Редактировать** (только свои, не старше 30 минут, типы `text`/`image`/`album`) →
   **Копировать текст** (текст или подпись; скрыт для стикеров/подарков и в чатах с запретом пересылки `noForwards`) →
   **Переслать** (скрыт при `noForwards`) → **Удалить** (только свои, красным, с подтверждением).
3. Для сообщений, которые ещё отправляются или загружаются, меню не показывать.
4. Закрывается по тапу мимо / назад; на веб-версии — также по Esc, прокрутке, изменению размера.

В личном чате с блокировкой (§2) реакции и «Ответить»/отправка невозможны: сервер откажет, поэтому в меню лучше скрыть эти пункты.
