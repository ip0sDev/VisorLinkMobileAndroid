# VisorLink Android — инвентарь скинов ID-карты, обмен в чатах, сессии Android

Спецификация для Android-клиента (**Kotlin**, **Jetpack Compose**, **Firebase Android SDK**) по изменениям
веба от 2026-10-06 (план — `TODO.md` §11.10). Базовые ID-карты (модель `idCards`, режимы, отрисовка карты,
тема по контексту) описаны в прежней спецификации — `docs/ANDROID_ID_CARDS_SPEC.md` (смотреть в истории git,
если её нет в рабочей копии). Здесь — только новое и изменённое.

**Сервер и правила уже задеплоены.** Android только читает данные, вызывает callables и повторяет
интерфейс. **Писать в `idCards/**`, `idTrades/**` и сессии напрямую нельзя** — правила запрещают,
всё делают Cloud Functions (регион `europe-west1`).

## Часть 1. Инвентарь скинов

### 1.1. Понятия

- **Скин** — бланк карты: `seed` → признаки (`traits`) и серийный номер. Это ровно то, что раньше было
  «внешним видом выпуска». **Режим и вид (`mode`, `species`) — свойства владельца, не скина**: один и тот же
  скин у Standard- и Protogen-пользователя рисуется в их режиме.
- **Надетый скин** — тот, что сейчас на карте (`idCards/{uid}.skinId`). Он **тоже занимает слот**.
- **Слоты:** 5 базовых, докупаются по одному за 100 Bits, максимум 20.
- **Прокрутка:** раз в 7 дней, 200 Bits, только при свободном слоте. Новый скин ложится в инвентарь,
  автоматически **не** надевается.
- **Продажа сервису:** +100 Bits, скин удаляется. Надетый продать нельзя.
- **Продавать скины друг другу за Bits нельзя** — только обмен скин на скин (часть 2).
- «Заменить документ» больше нет — его заменила прокрутка.

Константы (как на сервере):

```kotlin
const val ROLL_COST_BITS = 200
const val SELL_PRICE_BITS = 100
const val SLOT_PRICE_BITS = 100
const val BASE_SLOTS = 5
const val MAX_SLOTS = 20
const val ROLL_COOLDOWN_MS = 7L * 24 * 3600 * 1000
const val TRADE_NOTE_MAX = 140
```

### 1.2. Модель данных (читать; писать — только сервер)

#### `idCards/{uid}` — новые поля
```jsonc
{
  // ...прежние поля: mode, species, serial, traits, issuedAt, registeredAt, modeChangedAt, reissuedAt, version
  "skinId": "aB3x…" | null,   // надетый скин; у карт, выданных до инвентаря, нет (см. 1.3)
  "slots": 5,                 // 5…20
  "rolledAt": 1791200000000,  // последняя прокрутка, мс
  "equippedAt": 1791200000000 // последнее надевание, мс
}
```
При надевании сервер копирует в карту `serial`, `traits` и `issuedAt = skin.mintedAt` — поэтому код
отрисовки карты менять не нужно, он по-прежнему читает `idCards/{uid}`.

#### `idCards/{uid}/skins/{skinId}` — скин (читает только владелец)
```jsonc
{
  "seed": 123456789,
  "serial": "VL-7KQM-3XPA",
  "traits": { /* как в idCards: seed, finish, laminated, wear, foil, variant, tilt */ },
  "edition": "common" | "uncommon" | "rare" | "epic" | "legendary",
  "mintedAt": 1791200000000,     // когда бланк напечатан
  "obtainedAt": 1791200000000,   // когда попал к текущему владельцу
  "origin": "issue" | "roll" | "trade",
  "trades": 0,                   // сколько раз скин менял владельца
  "listedIn": "tradeId" | null   // выставлен в открытом обмене
}
```
`edition` хранится, но у старых записей может отсутствовать — тогда считать по `traits` (формула в старой
спецификации, `editionOf`).

### 1.3. Карты, выданные до инвентаря

У старых карт нет `skinId`, и подколлекция `skins` пуста. **Сервер переносит их сам** при первом любом
действии с инвентарём (прокрутка, надевание, продажа, слот, обмен): бланк текущей карты становится первым
скином. До этого клиент должен показывать текущую карту как **единственный надетый скин** (виртуальный,
без действий) и считать, что занят 1 слот из `slots ?: 5`. В вебе — `inventoryOf()` в `src/hooks/useIdSkins.js`.

Время последней прокрутки для кулдауна: `rolledAt ?: reissuedAt ?: issuedAt`.

### 1.4. Callable `idSkinInventory`

Один callable, действие — в `action`. Возвращает `data`.

| `action` | Параметры | Ответ | Что делает |
|---|---|---|---|
| `roll` | — | `{ skin: Skin & { id } }` | −200 Bits, новый скин в инвентарь |
| `equip` | `skinId` | `{ card }` | Надеть; если скин был выставлен на обмен — обмен закрывается |
| `sell` | `skinId` | `{ bits: 100 }` | +100 Bits, скин удалён; открытый обмен с ним закрывается |
| `buySlot` | — | `{ slots }` | −100 Bits, +1 слот |

Ошибки — `HttpsError`, причина в `details.reason`:

| `reason` | Когда | Текст (RU) |
|---|---|---|
| `cooldown` (+ `details.waitMs`) | прокрутка раньше 7 дней; надевание чаще раза в 3 с | «Слишком часто. Попробуйте через {wait}.» |
| `not-enough-bits` | не хватает Bits | «Нужно {n} Bits.» |
| `no-slot` | прокрутка без свободного слота | «В инвентаре нет свободного слота.» |
| `max-slots` | уже 20 слотов | «Больше слотов купить нельзя.» |
| `equipped` | продать/выставить/предложить надетый | «Надетый скин нельзя продать или обменять.» |
| `no-skin` | скина нет в инвентаре | «Такого скина нет в инвентаре.» |
| `no-card` | карта не выдана | — |

Все строки интерфейса — ключи `idskin.*` в `src/locales/{ru,en}.json` (там же тексты ошибок
`idskin.err.<reason>`).

### 1.5. Изменения в существующих callables

- **`issueIdCard`** — при первой выдаче сразу создаёт первый скин (`origin: 'issue'`), ставит `skinId`,
  `slots: 5`, `rolledAt`. Параметры и ответ прежние.
- **`reissueIdCard`** — больше не работает: всегда `failed-precondition`, `reason: 'outdated'`
  («Обновите приложение»). Кнопку «Заменить документ» на Android убрать, заменить инвентарём.

### 1.6. Интерфейс (настройки → «ID-карта»)

Блок «Инвентарь скинов» под выбором режима (веб: `IdSkinInventory.jsx`):

1. **Шапка:** заголовок, баланс Bits (из `users/{uid}.bits`, обновляется живой подпиской), счётчик
   «занято/слотов».
2. **Панель прокрутки**, одно из состояний:
   - кулдаун — кольцо прогресса недели и «Следующая прокрутка через {wait}»;
   - нет слота — «Нет свободного слота: продайте скин или купите слот», кнопка неактивна;
   - не хватает Bits — «Нужно 200 Bits», кнопка неактивна;
   - доступна — заметная кнопка «Прокрутить · 200 Bits» → подтверждение «Крутим? Спишется 200 Bits…» →
     экран прокрутки (1.7).
3. **Сетка слотов:** скины (мини-карта в режиме владельца, значок тиража, отметки «надет» ✓ и «на обмене» ⇄,
   полоса цвета тиража снизу), пустые слоты (вдавленный «карман» с пунктирным контуром), плитка
   «+ Ещё слот · 100 Bits» с подтверждением (если слотов < 20), иначе «Максимум — 20 слотов».
   Новые скины (после прокрутки или обмена) коротко подсвечиваются.
4. **Нажатие на скин** → лист скина (веб `IdSkinSheet.jsx`): крупная карта (можно вертеть и перевернуть),
   тираж, таблица признаков (отделка, голограмма, ламинирование, потёртость, оттенок n/12, серийник,
   «Получен: прокрутка/обмен/при выдаче · дата», «Обменов: n»). Кнопки: «Надеть» и «Продать за 100 Bits»
   (с подтверждением). У надетого — без кнопок, подсказка «Чтобы продать или обменять, сначала наденьте
   другой». Подсказка про обмен: «откройте чат → скрепка → «ID-карта на обмен»».

Цвета тиражей (как у названия тиража на обороте карты): common `hsl(215 12% 66%)`, uncommon
`hsl(150 62% 54%)`, rare `hsl(212 88% 64%)`, epic `hsl(276 80% 70%)`, legendary `hsl(42 95% 58%)`.

### 1.7. Экран прокрутки (веб `IdSkinRoll.jsx`)

Порядок: **сначала** вызов `roll` (показать «Печатаем бланк…»), **потом** анимация с уже известным скином.

1. **Барабан** (~6,4 с): горизонтальная лента ~54 лёгких плашек (не полных карт — только материал,
   полоса тиража и кружок голограммы), выигрышная на позиции 46. Ленту двигать одной анимацией смещения с
   сильным замедлением (в вебе `cubic-bezier(0.06, 0.62, 0.1, 1)`), остановка с небольшим случайным сдвигом
   внутри плашки, затем короткая «доводка» к центру. Стрелка сверху/снизу по центру; на каждой пересечённой
   плашке — вздрагивание стрелки и лёгкая вибрация (не чаще раза в 70 мс). Соседние с выигрышем плашки
   иногда заменяются на epic/legendary — «чуть-чуть не хватило». Ширина плашки — примерно ширина окна / 3,4
   (96–150 dp). После остановки выигрышная плашка увеличивается и светится цветом тиража, остальные тускнеют.
2. **Раскрытие:** карта влетает с переворотом (из обратной стороны, с лёгким перелётом), за ней вращающиеся
   лучи и свечение цвета тиража, ударная волна (у legendary — две) и разлёт искр (количество по тиражу:
   10 / 18 / 26 / 36 / 56). Название тиража появляется по буквам; у legendary — переливающееся золото.
   Затем признаки чипами и кнопки «В инвентарь» и «Надеть сейчас» (→ `equip`).
3. При «уменьшить анимацию» (системная настройка) — без барабана и эффектов, сразу результат.

## Часть 2. Обмен скинами в чатах

### 2.1. Правила

- Только **скин на скин**, никаких Bits.
- Только в **личных чатах и группах** (не в каналах, не с ботами).
- Выставить можно ненадетый скин, причём каждый скин — только в одном открытом обмене.
- Предложить можно любой ненадетый скин. **Одно предложение от человека на обмен**: повторное заменяет
  прежнее.
- Автор обмена принимает одно предложение — скины меняют владельцев в одной транзакции, остальные
  ожидающие предложения становятся `void`. Если надеть или продать выставленный скин, обмен закрывается.

### 2.2. Модель данных

#### Сообщение в чате: `chats/{chatId}/messages/{messageId}`, `type: 'id_trade'`
Пишет **только сервер** (при выставлении):
```jsonc
{
  "senderId": "uid", "senderUsername": "iposdev",
  "type": "id_trade",
  "tradeId": "Tr4d3…",          // ← главное поле
  "text": "Меняю на золото",    // подпись автора (может быть пустой) — для превью и поиска
  "createdAt": <serverTimestamp>, "seq": 123, "readBy": ["uid"], "reactions": [], "deleted": false
}
```
`chat.lastMessage = { type: 'id_trade', text: '🪪 ID-карта на обмен', senderId, senderUsername, readBy }`.
Превью в списке чатов и в цитате ответа: «🪪 ID-карта на обмен» / «🪪 ID card trade».

**Само сообщение ничего не доказывает** (клиенты могут создавать сообщения любого `type`). Вид скина и
статус брать только из `idTrades/{tradeId}`, и показывать карточку, лишь если
`trade.chatId == chatId && trade.messageId == message.id`. Иначе — «Обмен недоступен».

#### `idTrades/{tradeId}` — читают участники чата
```jsonc
{
  "chatId": "…", "messageId": "…",
  "ownerUid": "…", "ownerName": "iposdev",
  "skinId": "…",
  "skin": { "seed": 1, "serial": "VL-…", "traits": { … }, "edition": "epic" },  // снимок вида
  "note": "Меняю на золото",
  "status": "open" | "done" | "closed",
  "closedReason": "owner" | "equipped" | "sold" | "traded",   // при closed
  "offerCount": 2,                       // ожидающих предложений
  "deal": null | { "offerId", "fromUid", "fromName", "skinId", "skin": { … } },  // при done
  "createdAt": 0, "updatedAt": 0
}
```

#### `idTrades/{tradeId}/offers/{uid}` — id документа = uid предложившего
```jsonc
{
  "fromUid": "…", "fromName": "foxy",
  "skinId": "…", "skin": { "seed", "serial", "traits", "edition" },
  "status": "pending" | "accepted" | "declined" | "withdrawn" | "void",
  "createdAt": 0, "updatedAt": 0
}
```
Читать может автор предложения (свой документ) и автор обмена (все, в т. ч. запрос
`where status == 'pending'`).

### 2.3. Callable `idSkinTrade`

| `action` | Параметры | Ответ | Кто |
|---|---|---|---|
| `post` | `chatId`, `skinId`, `note?` (до 140 символов, одна строка) | `{ tradeId, messageId }` | участник ЛС/группы (не в муте) |
| `offer` | `tradeId`, `skinId` | `{ offerId }` | участник чата, не автор |
| `accept` | `tradeId`, `offerId` | `{ ok: true }` | автор обмена |
| `decline` | `tradeId`, `offerId` | `{ ok: true }` | автор обмена |
| `withdraw` | `tradeId` | `{ ok: true }` | автор предложения |
| `close` | `tradeId` | `{ ok: true }` | автор обмена |

Дополнительные `reason` (тексты — `idskin.err.<reason>`): `already-listed` (+ `details.tradeId`),
`trade-closed`, `offer-gone`, `owner-skin-gone`, `offer-skin-gone` (предложение при этом становится `void`),
`self-trade`, `chat-type`, `no-trade`, `equipped`, `no-skin`.

### 2.4. Интерфейс

**Выставить:** в меню вложений (скрепка) — пункт «ID-карта на обмен» (только ЛС и группы, не бот;
в вебе — ещё флаг `id_cards_enabled`, на Android флага нет) → окно выбора скина (веб `IdSkinPicker.jsx`, `purpose='post'`): сетка своих
скинов, надетый и уже выставленные недоступны, поле «Подпись — необязательно» (140) → «Выставить».
Пустое состояние: «Нечего выставить: надетый скин обменять нельзя. Прокрутите новый…».

**Карточка в чате** (веб `IdTradeMessage.jsx`), ширина ~320 dp, но не шире экрана:
- шапка «⇄ Обмен ID-картой» + значок тиража;
- **скин рисуется на карте смотрящего** — его режим, имя, ник, аватар («Примерка: так скин будет выглядеть
  на вашей карте»). Так чужой особый режим не раскрывается. В маске (Mask Mode) — режим Standard;
- подпись автора;
- действия по состоянию:
  - чужой открытый обмен → «Предложить обмен» → тот же выбор скина (`purpose='offer'`) с блоком
    «их карта ⇄ ваша»;
  - есть своё ожидающее предложение → мини-карта своего скина, «Ваше предложение ждёт ответа», «Отозвать»;
  - своё предложение `declined` / `void` → строка об этом и снова «Предложить обмен»;
  - свой открытый обмен → «Предложения (N)» (N = `offerCount`) и «Снять с обмена»;
  - `done` → две мини-карты с ⇄ и «Обмен состоялся: @автор ⇄ @предложивший». Если статус сменился на
    глазах — карты меняются местами, искры, вибрация;
  - `closed` → карта обесцвечена, «Снято с обмена» (`closedReason == 'owner'`) или «Скин больше
    недоступен для обмена».

**Предложения** (для автора, веб `IdTradeOffers.jsx`): свой скин сверху, список предложений (мини-карта,
@ник, тираж, отделка · голограмма), кнопки «Отклонить» и «Обменять» → «Точно меняем» → `accept`. После
успеха — анимация обмена (~2,6 с): две карты сходятся, меняются местами по дугам, вспышка в центре, искры,
надпись «Обмен состоялся!».

Подписки: `idTrades/{tradeId}` — для каждой видимой карточки; `offers/{myUid}` — если обмен чужой и
открыт; `offers where status == 'pending'` — только в окне предложений автора.

## Часть 3. Сессии Android-приложения

Раньше вход с Android записывался с User-Agent `okhttp/…` и показывался как «Неизвестное устройство».

### 3.1. Сервер

`registerSession` теперь определяет платформу **по App Check**, а не по словам клиента: если токен App Check
подтверждён и его `appId` — Android-приложение (`1:…:android:…`), сессия записывается как Android.
Только в этом случае сервер принимает необязательные поля об устройстве.

**Что нужно от Android:** вызывать `registerSession` (как и раньше, при каждом запуске) **с токеном
App Check** (Play Integrity) и с данными:
```kotlin
functions.getHttpsCallable("registerSession").call(mapOf(
    "deviceModel" to "${Build.MANUFACTURER} ${Build.MODEL}",  // до 60 символов, напр. "Google Pixel 8"
    "osVersion" to Build.VERSION.RELEASE,                     // до 20, напр. "14"
    "appVersion" to BuildConfig.VERSION_NAME,                 // до 20, напр. "1.4.0"
))
```
Без App Check поля игнорируются, и сессия считается веб-сессией.

### 3.2. Модель `users/{uid}/sessions/{sessionId}` — новые поля
```jsonc
{
  // прежние: createdAt, lastSeenAt, userAgent, tfaVerifiedAt
  "client": "android" | "ios" | "web",
  "appVerified": true,          // App Check подтвердил официальное приложение
  "deviceModel": "Google Pixel 8",   // только для android
  "osVersion": "14",
  "appVersion": "1.4.0"
}
```

### 3.3. Старые сессии

- При входе из подтверждённого Android-приложения сервер сам помечает прежние сессии этого пользователя
  с User-Agent `okhttp/…` или `Dalvik/…` как `client: 'android'`.
- Для всех пользователей разом есть миграция в админке веба («Пользователи → Сессии Android»).
- Клиенты всё равно должны распознавать `okhttp/` и `Dalvik/` как Android, даже без `client`.

### 3.4. Подпись в списке сессий (как в вебе, `describeSession`)

- Android: «VisorLink {appVersion} · {deviceModel} · Android {osVersion}». Отсутствующие части опускаются,
  минимум — «VisorLink · Android». Иконка — телефон.
- Остальное — по User-Agent (браузер · ОС), как раньше.
